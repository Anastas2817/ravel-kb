# Contributing

Документ написан с прицелом на будущее развитие; сейчас все правила применяю к себе в одном лице.

## Сборка и тесты

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure
```

Требования: CMake ≥ 3.20, C++17, Qt 6 (Widgets). Зависимости (GoogleTest, nlohmann/json) подтягиваются через `FetchContent`.

## Архитектурные правила

1. **`core/` не зависит от Qt.** Только стандартная библиотека C++17. Проверяется CI-целью `core` без Qt. Обоснование — [docs/architecture.md](docs/architecture.md) §1.1.
2. Все мутации графа — через классы `Command` (см. [docs/architecture.md](docs/architecture.md)).
3. Новые инварианты модели — только с тестами, их нарушающими.
4. Алгоритмы (раскладка) — за `ILayoutAlgorithm`, не зашиты в UI.

## Стиль кода

- C++17, `clang-format` (конфиг в репозитории), `-Wall -Wextra`.
- `-Werror` не включён глобально (не блокирует сборку в чужих окружениях с другими версиями компилятора), но перед PR локально проверяйте, что код собирается с `-Wall -Wextra` без новых предупреждений.

- В CI `-Werror` **включён** для целей `core` и `app`: новые предупреждения блокируют сборку. Локально `-Werror` не включён глобально — это позволяет собирать проект в чужих окружениях с другими версиями компилятора, не блокируя сборку из-за предупреждений, не относящихся к твоему коду. Правило: если локальная сборка с `-Wall -Wextra` даёт новые предупреждения в твоём коде — исправь их до PR. CI поймает, если не исправишь, но лучше не доводить.
- `enum class` вместо голых `enum`; `std::optional` вместо «магических» значений; `using NodeId = uint64_t;` для идентификаторов.
- Комментарии и имена — на английском; документация API — для Doxygen.

## Коммиты и ветки

Проект ведётся в одиночку — поэтому trunk-based: `main` — единственная постоянная ветка, повседневные изменения коммитятся туда напрямую, в том числе промежуточные состояния. История ничего не теряет, откат ошибки — `git revert`.

- **Короткоживущие ветки — только для рискованных экспериментов**, где заранее известна точка решения «мержим или выбрасываем» (пример: этап 3b роадмапа с лестницей деградации F1→F2/F3). Имя — `experiment/<короткое-имя>` от `main`. Ветка либо мержится, либо удаляется; долгоживущих веток нет.
- **Теги на вехи**: `git tag -a stage1-core -m "ядро: модель + JSON round-trip + тесты"` — рабочие состояния, к которым есть смысл возвращаться (этапы [roadmap.md](docs/roadmap.md), MVP).
- **Коммиты**: короткий императив («add Sugiyama layering», не «added»); опциональный префикс области (`build:`, `docs:`, `feat:`, `fix:`, `test:`) — как в истории репозитория. Один коммит — одна логическая правка.

### Для будущих контрибьюторов (когда появятся)

- Ветки: `feature/<короткое-имя>` от `main`; один PR — одна логическая задача.
- PR не мержится без зелёного CI и без новых предупреждений `-Wall -Wextra` в коде PR.

## Issues и PR

- Баг: шаги воспроизведения, ожидаемое/фактическое поведение, версия коммита.
- Фича: ссылка на раздел [docs/spec.md](docs/spec.md); если раздела нет — сначала обсудить в issue.
- Архитектурные решения (ADR) **рекомендованы, но не обязательны**: достаточно для ключевых, необратимых или дорогих в переделке решений (ядро без Qt, JSON, Command, id-политика). Мелкие решения — в комментариях/PR-описании. Шаблон ADR: контекст → решение → последствия, в `docs/adr/`.
