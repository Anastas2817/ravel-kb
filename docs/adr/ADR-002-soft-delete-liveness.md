# ADR-002: Soft-delete — живость как членство в индексе, без производных структур

**Статус:** принят (2026-10-11); реализация — неделя 5, до постройки команд undo/redo.

**Контекст.** Неделя 9 планирует undo/redo на командах. Текущая семантика удаления (ADR-001): слот зануляется фиктивным объектом (id 0), живость читается из слота (рёбра) или из `access_` (узлы) — два разных принципа для одного понятия. Команда удаления вынуждена хранить удалённые данные для undo, что размножает копии и риск рассинхронизации. Разбор к ревью (2026-10-11) показал: идемпотентность удаления держится на побочном эффекте очистки слота, а итерация по плотным векторам извне не имеет sanctioned-способа отличить живое от «дырки».

**Решение.** Удаление — софт-делит: данные в слоте сохраняются, из `access_` запись удаляется (каскадно — с инцидентными рёбрами). Живость выводима и единообразна для всех сущностей: **сущность жива ⟺ её членство в `access_`** (ребро — членство в `access_[from]` / `access_[to]`; узел — наличие записи). Никаких новых структур в домене: поля остаются `nodes_`, `relations_`, `access_` — меняется семантика удаления (отзыв членства вместо уничтожения данных) и добавляются Restore-методы. Формат файла не меняется: снапшот по-прежнему пишет только живых. Единственная точка чтения перебором — `ForEachLiveNode(fn)` / `ForEachLiveRelation(fn)` (callback с возвратом `bool` для досрочного выхода; фильтр по плотному вектору в ид-порядке); `ToSnapshot` переписывается через них же.

**Отклонённые альтернативы.**

- **A. Зомби + жёсткое удаление (текущее).** Команды тяжёлые (хранят данные), принципы живости двойственны, undo не проще, чем у C. Отклонён.
- **C. Зомби + мементо-команды.** Не трогает тесты недель 1–3, оставлен запасным путём: если переход на B зайдёт в тупик, возврат — в C, а не в A.
- **B с кэшем `alive_relations`.** O(1) `HasRelation` ценой хранимой производной структуры; избыточен при лимите 10³ сущностей. Оставлен как запасной ход «если профилирование покажет» (по аналогии с F2/F3 раскладки): добавить индекс позже тривиально, убрать после защиты — неприятно.

**Следствия (честные, включая цену).**

1. **undo/redo.** Добавление/удаление — машина состояний над членством, копии данных не нужны. Мутации атрибутов (`MoveNode`, будущие правки title/description) по-прежнему требуют мементо (старые значения) — мементо-команды не исчезают, а сокращаются до класса «изменение данных». *Уточнение (разбор 2026-10-11):* каскадная команда `DeleteNodes` не чистый `(id, операция)` — она обязана хранить id каскадно удалённых рёбер, чтобы undo восстановил ровно их и не воскресил ребро, удалённое пользователем после узла, но до undo. Лёгкие id, не данные, но слоган «команды = id-only» держится только у `Add*` и одиночных `DeleteRelation` — именно самая частная команда из него выпадает, к вопросам на защите готовиться следует.
2. **Перекрёстная проверка утрачена и заменена тестами.** Раньше рассогласование «слот vs `access_`» самодиагностировалось; при единственном источнике истины ошибка индекса незаметна для модели. Компенсация — тесты-инварианты (членство ⇔ инцидентность, каскадность удаления), в духе правила 17.
3. **Контракт идемпотентности пересматривается.** «Контракт удаления» и правило 27 (implementation.md) описывают зомби-семантику; при B повтор id в списке на удаление меняет поведение (мёртвый на момент применения). *Решение, принятое вместе с переходом:* id, мёртвый **до** вызова, — ошибка (`out_of_range`, как сейчас, негативные тесты сохраняются); повтор id **внутри одного вызова** — допустим и игнорируется (критерий правила 27 выполнен: «удалить n дважды» = «удалить n», результат единственный). Реализация обязана различать эти случаи — валидация до применения, а не проверка по ходу. Тесты `DuplicateIdsInArgument` переписываются в той же правке; формулировка правила 27 обобщается.
4. **Память модели растёт монотонно** в пределах сессии (слоты не освобождаются); принято с допущением «сброс при save/load», плюс перспектива «сжатый формат без дырок» (perspectives).
5. **«Тихие трупы»**: удалённая сущность выглядит валидной, пока не спросить индекс. Лечится теми же `ForEachLive*` и `HasNode`/`HasRelation` как единственными sanctioned-читателями живости (правило 14 доведено до всех сущностей).
6. **ADR-001 частично superseded**: счётчики, векторное хранение и «индекс = id − 1» остаются в силе; отменяется только пункт «удалённые слоты — фиктивными объектами (id 0)». *Дополнение (разбор 2026-10-11):* монотонность счётчиков перестаёт быть удобством сериализации (ADR-001) и становится требованием корректности undo: стеки команд хранят id, повторная выдача id после удаления воскресила бы не ту сущность — молча и необратимо. Следствие: счётчики никогда не уменьшаются в пределах сессии; компактификация («сжатый формат без дырок», perspectives) — только через save/load, то есть граница сессии, никогда «на лету».
7. **Смена режима отказа: с «громкого мусора» на «тихое правдоподобие».** Сентинел id 0 был не только маркером, но и слоем fail-loud: пропущенная проверка живости выдавала пустые поля — видимую чушь. При B пропущенная проверка выдаёт актуально выглядящие устаревшие данные (title, тип, позиция трупа читаются как настоящие). Ошибка переходит из «всплывёт сама» в «всплывёт, только если спросили индекс». Компенсация: `ForEachLive*` как единственная sanctioned-точка чтения перебором и тесты-инварианты (см. п. 2) — формулируется как смена режима отказа, а не как «лечится итераторами».
8. **`HasRelation` теряет тотальность и независимость.** Был: O(1), `noexcept`, зависел только от данных ребра — можно спросить про любой id в любой момент. Стал: читать `from` из слота → проверить живость `from` → искать в `access_[from]` (O(deg), связность с индексом узлов). Две обязанности реализации: (а) порядок проверок — мёртвый `from` означает мёртвое ребро и короткое замыкание **до** касания `access_` (иначе `.at()` бросит исключение внутри проверки живости); (б) инвариант 4 перестаёт быть проверяемым утверждением и становится частью определения `HasRelation` — живость ребра зависит от корректности индекса узлов.
9. **Налог трупов на операции над графом целиком.** Корпус занимает не только память: копирование `Graph` и любые будущие целографные операции (ветвление, сравнение графов) тащат мёртвые данные, если не фильтровать. `ForEachLive*` закрывает перебор, но не копирование. На масштабе 10³ ничтожно; принципиально — точка, где A была «чистее».
10. **Мелкие, для полноты.** В минус: отладка — `id == 0` виден в дебаггере мгновенно, правдоподобный труп требует проверки через индекс; `ToSnapshot` становится O(R·deg) вместо O(R) (поиск членства при фильтрации) — на лимите проекта несущественно. В плюс: перспектива «сжатый формат без дырок» обретает настоящее назначение (возвращает память), а не косметику; ссылки на живые сущности (`const Node&` из геттеров) стабильны между удалением и undo — слот не перезаписывается.

**Связность по границам (разбор 2026-10-11).** Переход не двигает метрики связности равномерно — он её перераспределяет:

- **Ядро внутри: ↑, концентрированно.** Было два независимых механизма живости (узлы — `access_`, рёбра — слот), их рассогласование работало бесплатным оракулом. Стало: определение живости рёбер опирается на `access_` — структуру узловой стороны; `HasRelation` читает данные ребра и индекс узлов; Restore обязан соблюдать порядок (узел до рёбер); инвариант 4 — часть определения, а не проверяемое утверждение. Связность выросла не по всему ядру, а в одной точке: определение живости перестало быть локальным к виду сущности. Осознанный обмен: независимость двух механизмов против единства одного принципа; для класса-контейнера разумный, для пары классов был бы подозрительным.
- **Core → storage: ≈ 0.** `GraphSnapshot` всегда содержал только живых, формат не меняется; переход не трогает самый тонкий внешний контракт проекта.
- **Core → app: ↓, осязаемо.** Под A стек undo в app хранил полные DTO (`Node`/`Relation`) — app был связан с полевым составом ядра (новое поле `Relation` = правка команды). Под B стек хранит id: app знает о сущностях то же, что всегда (id есть), внутренности не знает. Мутации атрибутов (`MoveNode`) оставляют в стеке пару double — точечная связность с полями `Node` остаётся только там, где принципиальна (данные, не членство).
- **Core → UI: ≈ 0, качественный плюс.** API-поверхность та же (`HasNode`/`HasRelation`/события); плюс — объяснимость: «живое = в индексе» одна фраза, зомби-семантику с дырками пришлось бы объяснять параграфом.

Ответ на вопрос «куда девается сложность» (стандартный на защите): наружу не выходит — концентрируется внутри ядра одной связкой «живость рёбер ↔ индекс узлов», оплачивается тестами-инвариантами (следствие 2).
