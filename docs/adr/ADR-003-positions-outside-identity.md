# ADR-003: Позиции вне идентичности — `positions_`, плотный вектор параллельно `nodes_`

**Статус:** принят (2026-10-17); реализация — отдельной правкой (затрагивает `Node`, `GraphSnapshot`, storage, `MoveNodeCmd`, round-trip тесты). До реализации формат v2 остаётся действующим; ADR фиксирует направление, чтобы развилка не переоткрывалась.

**Контекст.** R6 (2026-09-21) закрыл позицию как `std::optional<std::pair<double,double>>` внутри `Node`. К моменту подхода этапа 3 (раскладка) накопилось три давления на это решение. (1) Большинство узлов получают позицию от раскладки, а не от руки: поле по природе вычислимо, а «вычислимое в модели не хранится» (позиция при этом — данные пользователя при ручной расстановке, см. отклонённую альтернативу C). (2) Призрачные иерархии (perspectives §2) требуют per-view позиций — view-данные внутри идентичности узла размножатся или потребуют дублирования полей. (3) Undo позиции через летопись не должен трогать «содержание» узла: `MoveNodeCmd` правит DTO-идентичность ради view-атрибута. `Node` помечен `// DTO`, но фактически несёт view-поле, и всякая мутация позиции проходит через него.

**Решение.** `hand_position` покидает `Node`. `Graph` хранит **`std::vector<std::optional<Position>> positions_`** — плотный вектор с индексом `id − 1`, параллельный `nodes_` (та же дисциплина адресации, ADR-001/002; `nullopt` = позиция не задана, участок не выделен — назначит раскладка). `std::pair<double,double>` заменяется на `struct Position { double x, y; }` (доменное имя, а не геометрическое). `Node` остаётся идентичностью и содержанием. `MoveNode` и валидация nan/inf переезжают к `positions_`; комментарий «exact `==` для double — намеренно, раскладка не пользуется сравнением» переезжает к `Position`. `GraphSnapshot` получает отдельную секцию позиций **только живых узлов**; `format_version` → **3**. `SessionEqual` обязан сравнивать и `positions_` (иначе undo/move-тесты слепы к расхождениям позиций).

Первая версия решения записывала хранение как «side-map (`std::unordered_map<NodeId, Point>`)» — **исправлено до реализации**: главный потребитель — раскладка, свипы по слоям читают позиции последовательно, а мутации (undo) адресуют по id; плотный вектор даёт обоим прямое адресование `id − 1` без переходов по указателям и сохраняет единую индексную дисциплину модели.

**Отклонённые альтернативы.**

- **A. Оставить в `Node` (статус-кво).** View-данные в идентичности; per-view — дублирование полей или отдельные колонки в DTO; undo позиции мутирует содержание. Отклонено: см. контекст.
- **B. `std::unordered_map<NodeId, Position>` (первая версия этой записи).** Произвольный доступ в точках мутации (undo) и чтения (layout); нет параллельной индексации `id − 1`; промахи кэша против последовательных свипов; зомби-семантика неоднородна с остальной моделью. Записана для честности истории решения.
- **C. Чистый runtime-кэш без секции в файле.** Отвергнута пара «не сохранять позиции в JSON, пересчитывать раскладку на загрузке»: ручная расстановка — данные пользователя, терять её молча недопустимо.

**Следствия (честные, включая цену).**

1. **Формат файла v3.** Секция позиций пишется только для живых узлов; файлы v2 не читаются (поддержка предыдущих версий до первого публичного релиза не требуется — spec §4.5, формулировка уже зафиксирована). Spec потребует согласованной правки (§4.3 формат, §5.5 семантика ручной позиции) — одним коммитом с реализацией.
2. **Затрагиваемые места (чек-лист реализации):** `Node` (поле уходит, `operator==` меняется), `GraphSnapshot` (секция), storage Save/Load (v3), `MoveNodeCmd` (поле `Position`), round-trip тесты, эталон `app_tests` (`MoveNodeCmd.DoUndoRedo`), `SessionEqual`.
3. **Память: ещё один плотный вектор O(max_id).** `optional<Position>` ≈ 24 байта на слот; та же цена, принятая для `nodes_`/`relations_` (ADR-001/002), но суммарно налог растёт с каждым таким вектором — по правилу 31 каждый новый обязан приносить собственного потребителя; потребитель `positions_` — свипы раскладки (читают слой целиком, последовательно). *Уточнение (2026-10-17, замечание автора):* обоснование векторов для `nodes_`/`relations_` весомо опиралось на Сугияму как требовательного потребителя (implementation.md, R2-addendum) — с выносом позиций этот потребитель и весовая часть обоснования переехали в `positions_` (обоснование следует за потребителем, правило 31). Для `nodes_`/`relations_` остаются: прямое адресация `id − 1`, детерминизм итерации и сериализации, монотонность счётчиков (ADR-001) — без сугиямовского аргумента.
4. **Позиция наследует зомби-семантику бесплатно.** Удаление узла не трогает запись в `positions_` (живость определяет только `access_`, ADR-002); запись терпится до конца сессии (компактификация на границе сессии — save/load, как для трупов) и не попадает в снапшот. Следствие, которое стоит назвать явно: **undo удаления возвращает узлу его позицию без дополнительного механизма** — кадастровая запись переживает анабиоз вместе с досье.
5. **Смежное решение зафиксировано: `size` не выносится** (implementation.md R6, «граница аналогии»). Триггер пересмотра — день, когда размер станет вычислимым с ручным переопределением («PageRank для размера узлов», perspectives); до события — содержание `Node`.

**Связность по границам (по образцу ADR-002).**

- **Ядро внутри: ≈ 0, дисциплина усиливается.** `positions_` параллелен `nodes_` — третий вектор той же формы; общий принцип «индекс = id − 1, живость из `access_`» распространяется на view-данные без нового механизма.
- **Core → storage: ↑, осознанно.** Меняется самый тонкий внешний контракт проекта (формат файла, v2 → v3). Принято: git-friendly формат ещё не опубликован, стоимость смены сейчас минимальна и не будет падать с возрастом базы знаний.
- **Core → app: ≈ 0, качественный плюс.** `MoveNodeCmd` хранит `Position` вместо пары double — точечная связность та же; зато undo позиции перестаёт быть мутацией «содержания», оставаясь мутацией view-данных.
- **UI → core: ≈ 0.** Первоначальная запись «Core → UI: ↑» — ошибка направления: стрелок core → ui в архитектуре нет (зависимости идут ui → app → core), и чтение позиции и раньше шло через API Graph. Вынос добавляет к поверхности максимум один метод (`PositionOf(id)`), число точек чтения не растёт.
