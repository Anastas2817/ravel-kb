# ADR-004: `access_` — индекс инцидентности, а не список исходящих; петля регистрируется один раз

**Статус:** принят (2026-10-30); реализован тем же днём: `AddRelation`, `RestoreRelations`, `FromSnapshot` регистрируют петлю один раз, `EraseRelations` стирает один раз; тест `FindCycleHints.SelfLoopIsSingleEdgeHint`.

**Контекст.** Инвариант ADR-002 (graph.hpp): «r is listed in `access_[x]` if and only if x is from or to of r». Два давления на уточнение. (1) Петля (`from == to`): два безусловных `push_back` падали в **одну и ту же** запись, и id оказывался там дважды — негласная кратность «для петель всегда две копии», на которую молчаливо опирался `EraseRelations` (второй `find`/`erase` без двух копий — попадание в `end()`, UB). Первый реальный сбой: `ResolveRelationIds(a, a, ...)` возвращал `[id, id]`, и материализация циклов выдавала два одинаковых hint'а. (2) Поднятый при разборе вопрос: зачем вообще держать `to`-сторону в `access_`? Потребители «что касается узла» (каскад удаления, соседи, рёбра узла для отрисовки) не различают направление.

**Решение.** `access_` — индекс инцидентности: ровно один раз для каждой конечной точки; при совпадении концов — один раз (одна копия для петли). Регистрация петли одинакова во всех трёх точках создания записи (`AddRelation`, `RestoreRelations` — undo, `FromSnapshot` — загрузка); стирание — один раз (`EraseRelations`, условие `to != from` на втором erase). Рефлексивность — свойство **типа отношения** (флаг рядом с `symmetric`/`transitive` в онтологии), не особенность хранения: рефлексивный тип трактуется алгоритмами как «у каждого узла есть неявная петля этого типа» без физических дублей записей.

**Отклонённые альтернативы.**

- **A. Статус-кво (дубль для петель).** Негласный контракт, который нужно синхронно поддерживать в четырёх местах; любой путь, зарегистрировавший петлю один раз, ломает `EraseRelations`; `GetIncidentRelations` и `ResolveRelationIds` лгут про кратность. Отклонено после сбоя в материализации циклов.
- **B. Оставить дубль, дедуплицировать в `ResolveRelationIds`.** Симптоматическое лечение: `GetIncidentRelations` всё равно отдаёт `{id, id}`, негласный контракт никуда не девается.
- **C. Хранить только исходящие (`access_[from]`).** Каждый запрос «что касается узла» — каскад `DeleteNodes`, `GetNeighbors`, перечисление рёбер узла для отрисовки/Resync — потребует полного скана `relations_`: O(E) вместо O(deg). Отклонено.
- **D. Раздельные `out_` / `in_`.** Почти все потребители хотят обе стороны сразу: каждый запрос — два просмотра и слияние, плюс вторая структура под тот же инвариант живости. Отложено: пересмотреть, когда появится потребитель, которому нужна строго одна сторона (правило 31 — структура обязана приносить собственного потребителя).

**Следствия (честные, включая цену).**

1. Инвариант ADR-002 уточнён множественностью: «listed exactly once» — включая петли. Комментарий у `access_` в graph.hpp дополнен явной фразой.
2. **Формат файла не изменился.** `FromSnapshot` перестраивает `access_` при загрузке; старые файлы с петлями читаются корректно независимо от того, как они создавались.
3. Контракт `ResolveRelationIds`: возвращает только различные id, каждое ребро — не более одного раза. Материализация циклов опирается на это (декартово произведение кандидатов по парам пути).
4. Reflexive из perspectives — флаг типа отношения; потребует поля в онтологии формата при реализации (отдельным шагом, с поднятием `kFormatVersion`).
5. Цена раздельных out/in (альтернатива D) не измерялась: при текущих масштабах выигрыш нулевой, две структуры дороже одной.
