## 1. Слои (C2)

```
┌─────────────────────────────────────────────┐
│  UI (Qt 6 Widgets)                          │
│  Canvas (QGraphicsScene/View): визуализация │
│  и запросы; мутаций в модели не производит  │
├─────────────────────────────────────────────┤
│  App                                        │
│  Controller · Command (сценарии/команды) ·  │
│  SessionState — единственный источник мутаций│
├─────────────────────────────────────────────┤
│  Core (чистый C++17, без Qt)                │
│  Graph · GraphSnapshot · Layout ·           │
│  Algorithms · SampleGraphs                  │
├─────────────────────────────────────────────┤
│  Storage                                    │
│  JsonStorage (потоки, format_version)       │
└─────────────────────────────────────────────┘
        ↑ порядок зависимостей: UI → App → Core ← Storage
```

Ключевые правила потока данных (C2):

1. **App — единственный источник мутаций.** Все изменения модели приходят как сценарии/команды из App; UI напрямую граф не изменяет, а отправляет жесты пользователя в App (unidirectional data flow).
2. **Обратный поток — синхронные ответы, а не оповещения.** Все мутации рождаются в UI и проходят через App, поэтому пуш-подписка на изменения модели не нужна: запрос (`ExecuteAddNode`, …) возвращает результат (id, позиции, ошибки), UI обновляет сцену по ответу. Контракт `IGraphObserver` рассмотрен и отклонён (§2.3).
3. **Ядро не зависит от Qt** и не знает о Storage: сериализация проходит через нейтральный `GraphSnapshot`, который разбирает и валидирует сам `Graph` (фабрика `Graph::FromSnapshot`).

### 1.1. Почему ядро без Qt

Обоснование — не эстетика «чистоты», а измеримые выгоды:

1. **Тестируемость без GUI.** Все тесты ядра (инварианты модели, round-trip сериализации) запускаются headless: без оконного сервера, без Qt вообще. Сборка и прогон тестов ядра занимают секунды.
2. **CI дешевле и надёжнее.** CI-цель `core` собирается и тестируется без установленного Qt — меньше зависимостей, меньше шанс сломать сборку из-за окружения (см. `.github/workflows/ci.yml`).
3. **Дисциплина зависимостей.** Запрет Qt в ядре — автоматическая проверка границ слоёв: если для фичи «нужно немного Qt в core», это сигнал, что фичу спроектировали неверно (логика утекла в presentation).
4. **Переносимость и переиспользование.** Core — статическая библиотека; собирается под любую платформу и может быть переиспользована вне десктопного UI (CLI-утилиты, тестовые генераторы — см. потребители в perspectives.md).

Ядро использует только стандартную библиотеку C++17.

## 2. Компоненты (C3)

| Компонент | Слой | Назначение (одной фразой) | Статус |
|---|---|---|---|
| `Graph` | Core | хранить модель предметной области и поддерживать корректное состояние карты знаний | реализован |
| `GraphSnapshot` | Core | переносить состояние Graph между слоями без знания формата | реализован |
| `SampleGraphs` | Core | строить демонстрационный граф для разработки UI | заглушка (`MakeShowcaseGraph` без тела) |
| `Layout` | Core | преобразовывать граф в пространственную раскладку — выдавать координаты | запланирован (этап 3) |
| `Algorithms` | Core | анализировать структуру Graph: DFS, PageRank, циклы | запланирован (этап 3) |
| `JsonStorage` | Storage | сериализация/десериализация, валидация формата и версии | реализован (потоки) |
| `Controller` | App | обслуживать сценарии пользователя: создать/изменить/удалить узел/отношение | запланирован (этап 2) |
| `Command` | App | оформлять мутации с возможностью отката (undo/redo) | запланирован (этап 4) |
| `SessionState` | App | недавние файлы, активный инструмент, очередь undo/redo | запланирован (этап 2) |
| `Canvas` | UI | визуализировать Graph и Layout, отображать подсказки Algorithm | база (неделя 4): узлы перемещаемы, рёбра следуют |

Зависимости читателей: `Layout` и `Algorithms` — клиенты `Graph` («читает структуру»), Graph о них не знает. Это сознательный ответ на риск God Object: `Graph` отвечает только за корректное состояние, анализ и геометрия живут снаружи.

### 2.1. GraphSnapshot и проверяемая фабрика

Разбор формата (JSON) и восстановление модели разведены: `JsonStorage` понимает только байты и потоки, `Graph::FromSnapshot` — только семантику. Снимок — нейтральные данные без JSON; граф сам проверяет id, счётчики `next_id_*`, типы и концы связей и отклоняет некорректные данные.

Почему публичная фабрика — не дыра в инкапсуляции: публичность `FromSnapshot` не даёт возможности вставить произвольный id в существующий граф — публичного метода вставки с произвольным id нет и не будет. Новая сущность и восстановленная имеют разную семантику (первая получает новый id, вторая сохраняет прежний), и фабрика — единственная точка восстановления.

`format_version` намеренно **не** входит в снимок: версия — свойство файла/слоя storage, а не модели.

Что намеренно отложено: интерфейс `GraphSource`/второй полный формат (бинарный) — потребитель пока один; второй формат сможет создавать тот же снимок без новой абстракции. См. потребителей в perspectives.md.

### 2.2. JsonStorage без интерфейса IStorage

Сериализация работает с потоками (`std::istream`/`std::ostream`), а не с путями файлов — кто открывает файл, решает слой App (на C2 стрелки `LoadPath`/`SavePath` идут от App). Отдельный интерфейс `IStorage` не введён: граница «модель ↔ байты» уже тестируется round-trip через потоки в памяти, а второй реализации в обозримой перспективе нет (преждевременная абстракция). Если форматов станет два, обобщением послужит `GraphSnapshot`, а не интерфейс поверх JSON.

### 2.3. Отклонённый Observer: Graph никого не оповещает

Рассмотрен контракт `IGraphObserver` (ядро эмитит события мутаций, UI подписывается и перерисовывает). Отклонён (2026-10-09):

- **Нет внешних мутаторов.** Все изменения модели рождаются в UI и синхронно проходят через App: инициатор запроса тут же получает ответ (id созданного узла, результат операции). Пуш-уведомления нужны, когда модель меняется «сама» (коллаборация, фоновые процессы, плагины, пишущие мимо App) — в Ravel таких источников нет ни в MVP, ни в перспективах.
- **App и так знает обо всех мутациях** — он воронка команд: dirty-flag («сохранить перед выходом?»), автосейв, очередь undo/redo не нуждаются в наблюдении.
- **Pull-клиенты Graph не пострадали.** Layout/Algorithms читают модель целиком (`const Graph&` на входе каждого вызова) — для них событие «узел добавлен» бесполезно, нужен снимок всей структуры.
- **Поиск** — запрос (линейный проход по титулам, 10³ узлов — микросекунды), а не подписка.

Если когда-нибудь появится второй источник мутаций (плагины, синхронизация файла с диском), оповещение вводится **на границе App**, а не внутри Graph: Graph остаётся «немым» доменным объектом. Это согласуется с рекомендацией преподавателя (сериализация, история команд и алгоритмы развиваются за пределами Graph) и с правилом 21 implementation.md (абстракция поведения угадывается, данные — нет). Синхронность «запрос → ответ» — осознанное ограничение: пока мутация не «долгая», блокирующий вызов из UI проще очереди событий.

### 2.4. Что намеренно НЕ сделано абстракцией

- **`IStorage`** — см. §2.2: граница уже проверяема тестами, второй реализации нет.
- **`GraphSource`** — см. §2.1: отложено до появления второго полного формата.
- **Онтология лент** — конкретная конфигурация, а не стратегия: второй реализации нет и не предвидится.
- **Команды не сериализуются** — живут только в стеках undo/redo; логирование операций — из перспектив.

## 3. Паттерны проектирования

- **Factory (проверяемая)** — `Graph::FromSnapshot`: единственная точка восстановления модели с валидацией инвариантов (§2.1).
- **Mediator** — *роль слоя App.* Единственная точка, знающая всех участников (UI, Core, Storage): воронка `UI → App → Core ← Storage` вместо прямых связей UI↔Core и UI↔Storage. «Знает всех» здесь — не God Object: у App ноль предметных инвариантов, все решения делегируются; критерий God Object — количество ответственности, а не количество соседей. Знание UI односторонне не выходит: App возвращает данные в ответ на запрос, не вызывая код UI.
- **Observer** — *рассмотрен и отклонён* (§2.3): внешних мутаторов модели нет, обратный поток покрывается синхронными ответами на запросы.
- **Command** — *планируется (этап 4).* Все мутации графа оформляются командами с `do()/undo()`; история — стеки undo/redo. Альтернатива (снапшоты всего графа) проще, но дороже по памяти. Митигация риска: действия канваса (этап 2) с первого дня оформляются командами без стеков — тогда этап 4 добавляет только стеки.
- **Strategy** — *не введён сознательно.* Заменяемых алгоритмов пока нет: раскладка и анализ — отдельные классы клиенты Graph, а не подменяемые стратегии. Если появится вторая реализация раскладки — интерфейс будет введён тогда (YAGNI в обе стороны).
- **Composite** — *проектируемая возможность, в коде не используется.* Общий интерфейс «карта любого уровня вложенности» закладывается под фрактальную вложенность (perspectives.md), но без реального использования вводить его — мёртвый интерфейс.

## 4. Инварианты модели

Единый источник истины — [implementation.md](implementation.md), раздел «Инварианты Graph (сводно)» (дублирование намеренно устранено). Общий принцип: граф и только Graph следит за инвариантами; `FromSnapshot` обязан отклонять их нарушения.

## 5. Структура репозитория

```
ravel-kb/
├── core/            # чистый C++17: модель, снимок, свои контракты
│   ├── include/     # graph.hpp, sample_graphs.hpp
│   └── src/         # graph.cpp
├── app/             # Controller, Command, SessionState (каркас CMake)
├── ui/              # Canvas (Qt Widgets)
├── storage/         # JsonStorage (потоки, nlohmann/json)
│   ├── include/     # storage.hpp
│   └── src/         # storage.cpp
├── tests/           # GoogleTest: graph_test.cpp, storage_test.cpp
├── docs/            # spec, architecture, roadmap, perspectives, research,
│   │                # c1_scope, assets/ (в т.ч. C4-диаграммы)
│   └── assets/c4/   # C1.png … C4.png — источник истины по архитектуре
├── .github/         # CI (job core без Qt)
└── CMakeLists.txt
```
