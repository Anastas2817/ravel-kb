## 1. Слои (C2)

```
┌─────────────────────────────────────────────┐
│  UI (Qt 6 Widgets)                          │
│  Canvas (QGraphicsScene/View): визуализация │
│  и запросы; мутаций в модели не производит  │
├─────────────────────────────────────────────┤
│  App                                        │
│  Controller · Command (сценарии/команды) ·  │
│  SessionState — единственный источник мутаций│
├─────────────────────────────────────────────┤
│  Core (чистый C++23, без Qt)                │
│  Graph · GraphSnapshot · Layout ·           │
│  Algorithms                                 │
├─────────────────────────────────────────────┤
│  Storage                                    │
│  JsonStorage (потоки, format_version)       │
└─────────────────────────────────────────────┘
        ↑ порядок зависимостей: UI → App → Core ← Storage
```

Ключевые правила потока данных (C2):

1. **App — единственный источник мутаций.** Все изменения модели приходят как сценарии/команды из App; UI напрямую граф не изменяет, а отправляет жесты пользователя в App (unidirectional data flow).
2. **Обратный поток — синхронные ответы, а не оповещения.** Все мутации рождаются в UI и проходят через App, поэтому пуш-подписка на изменения модели не нужна: запрос (`Controller::AddNode`, …) возвращает результат (id, ошибки), UI обновляет сцену по ответу. Контракт `IGraphObserver` рассмотрен и отклонён (§2.3).
3. **Ядро не зависит от Qt** и не знает о Storage: сериализация проходит через нейтральный `GraphSnapshot`, который разбирает и валидирует сам `Graph` (фабрика `Graph::FromSnapshot`).

### 1.1. Почему ядро без Qt

Обоснование — не эстетика «чистоты», а измеримые выгоды:

1. **Тестируемость без GUI.** Все тесты ядра (инварианты модели, round-trip сериализации) запускаются headless: без оконного сервера, без Qt вообще. Сборка и прогон тестов ядра занимают секунды.
2. **CI дешевле и надёжнее.** CI-цель `core` собирается и тестируется без установленного Qt — меньше зависимостей, меньше шанс сломать сборку из-за окружения (см. `.github/workflows/ci.yml`).
3. **Дисциплина зависимостей.** Запрет Qt в ядре — автоматическая проверка границ слоёв: если для фичи «нужно немного Qt в core», это сигнал, что фичу спроектировали неверно (логика утекла в presentation).
4. **Переносимость и переиспользование.** Core — статическая библиотека; собирается под любую платформу и может быть переиспользована вне десктопного UI (CLI-утилиты, тестовые генераторы — см. потребители в perspectives.md).

Ядро использует только стандартную библиотеку C++23.

### 1.2. MVC: соответствие классическому тройственному разделению (зафиксировано 2026-10-24)

Трёхслойная схема §1 — это MVC в строгом смысле, с одним сознательным уточнением контроллера:

| Роль MVC | У Ravel | Поведение |
|---|---|---|
| **Model** | `Graph` (core) | Наблюдаемое состояние + инварианты. Не оповещает никого (§2.3) — «пассивная модель»: её меняют, с неё читают. |
| **View** | Сцена: `NodeItem`/`RelationItem`, `ResyncScene` | Проекция модели на экран. Хранит только идентификаторы сущностей (id) и эфемерное состояние взаимодействия (полупрозрачная линия жеста, точка старта драга). Ни одного указателя на модель, ни одной мутации — view сверяет себя с моделью через reconcile (`ResyncScene` по `Nodes()`/`Relations()`). |
| **Controller** | `Controller` + команды + `CommandChronicle` (app) | Единственная точка мутации модели. Принимает *намерения* UI («добавь узел», «перемести», «свяжи»), превращает их в команды, возвращает `expected` с ошибкой. Не хранит UI-состояния и не знает о сцене. |

Три следствия, которые стоит читать как правила:

1. **View ⇄ Model напрямую запрещены обе стрелки.** View не мутирует модель (все мутации — через Controller, инвариант 7); Model не пушит в View (нет Observer, §2.3 — обновление view по синхронному ответу контроллера и явному reconcile).
2. **Пассивная модель + reconcile вместо Observer.** View устроена «лениво и идемпотентно»: `ResyncScene` приводит сцену к read-модели целиком (создать/обновить/удалить по id). Это устойчивее подписки: undo/redo, открытие файла и внешние изменения проходят по одному пути, а не по N каналам оповещений. Цена — полный проход по сцене; на масштабах курсовой (10³ сущностей) пренебрежима, точка пересмотра — эпоха Layout.
3. **Контроллер тонкий, команда — носитель протокола.** Controller не содержит логики мутаций (она в `Graph::Add*` и в `Do` команды) и не содержит логики undo/redo (она в летописи). Его работа — трансляция DTO команд ↔ вызовы модели и владение сессией (файл, закладка сохранения). Поэтому одинаковые имена `AddNode`/`DeleteNodes` на трёх слоях — не дубль, а один сценарий, видимый с трёх этажей (см. R15).

Историческая справка для защиты: классический MVC (Smalltalk-80) имел *активную* модель с подпиской view; отказ от Observer здесь (§2.3, R12) — не отступление от MVC, а выбор его пассивной разновидности (MVP/MVVM-родословная «view сама себя обновляет по запросу»), продиктованный наличием команды как естественной границы и однопоточной синхронной природой сценариев.

## 2. Компоненты (C3)

| Компонент | Слой | Назначение (одной фразой) | Статус |
|---|---|---|---|
| `Graph` | Core | хранить модель предметной области и поддерживать корректное состояние карты знаний | реализован |
| `GraphSnapshot` | Core | переносить состояние Graph между слоями без знания формата | реализован |
| `Layout` | Core | преобразовывать граф в пространственную раскладку — выдавать координаты | запланирован (этап 3) |
| `Algorithms` | Core | анализировать структуру Graph: DFS, PageRank, циклы | запланирован (этап 3) |
| `JsonStorage` | Storage | сериализация/десериализация, валидация формата и версии | реализован (потоки) |
| `Controller` | App | обслуживать сценарии пользователя: создать/изменить/удалить узел/отношение | скелет: Open/Save/SaveAs через JsonStorage; сценарии мутаций — заглушки (этап 2, в работе) |
| `Command` | App | оформлять мутации с возможностью отката (undo/redo) | база реализована: `AnyCommand` (variant + concept) + `CommandChronicle`, 5 команд, `app_tests` (этап 4); подключение к UI — впереди |
| `SessionState` | App | состояние сессии: граф, летопись команд, путь к файлу, закладка сохранения | реализован как struct внутри `Controller`; «недавние файлы, активный инструмент» — не начато |
| `Canvas` | UI | визуализировать Graph и Layout, отображать подсказки Algorithm | база (неделя 4): узлы перемещаемы, рёбра следуют |

Зависимости читателей: `Layout` и `Algorithms` — клиенты `Graph` («читает структуру»), Graph о них не знает. Это сознательный ответ на риск God Object: `Graph` отвечает только за корректное состояние, анализ и геометрия живут снаружи.

### 2.1. GraphSnapshot и проверяемая фабрика

Разбор формата (JSON) и восстановление модели разведены: `JsonStorage` понимает только байты и потоки, `Graph::FromSnapshot` — только семантику. Снимок — нейтральные данные без JSON; граф сам проверяет id, счётчики `next_id_*`, типы и концы связей и отклоняет некорректные данные.

Почему публичная фабрика — не дыра в инкапсуляции: публичность `FromSnapshot` не даёт возможности вставить произвольный id в существующий граф — публичного метода вставки с произвольным id нет и не будет. Новая сущность и восстановленная имеют разную семантику (первая получает новый id, вторая сохраняет прежний), и фабрика — единственная точка восстановления.

`format_version` намеренно **не** входит в снимок: версия — свойство файла/слоя storage, а не модели.

Что намеренно отложено: интерфейс `GraphSource`/второй полный формат (бинарный) — потребитель пока один; второй формат сможет создавать тот же снимок без новой абстракции. См. потребителей в perspectives.md.

### 2.2. JsonStorage без интерфейса IStorage

Сериализация работает с потоками (`std::istream`/`std::ostream`), а не с путями файлов — кто открывает файл, решает слой App (на C2 стрелки `LoadPath`/`SavePath` идут от App). Отдельный интерфейс `IStorage` не введён: граница «модель ↔ байты» уже тестируется round-trip через потоки в памяти, а второй реализации в обозримой перспективе нет (преждевременная абстракция). Если форматов станет два, обобщением послужит `GraphSnapshot`, а не интерфейс поверх JSON.

### 2.3. Отклонённый Observer: Graph никого не оповещает

Рассмотрен контракт `IGraphObserver` (ядро эмитит события мутаций, UI подписывается и перерисовывает). Отклонён (2026-10-09):

- **Нет внешних мутаторов.** Все изменения модели рождаются в UI и синхронно проходят через App: инициатор запроса тут же получает ответ (id созданного узла, результат операции). Пуш-уведомления нужны, когда модель меняется «сама» (коллаборация, фоновые процессы, плагины, пишущие мимо App) — в Ravel таких источников нет ни в MVP, ни в перспективах.
- **App и так знает обо всех мутациях** — он воронка команд: dirty-flag («сохранить перед выходом?»), автосейв, очередь undo/redo не нуждаются в наблюдении.
- **Pull-клиенты Graph не пострадали.** Layout/Algorithms читают модель целиком (`const Graph&` на входе каждого вызова) — для них событие «узел добавлен» бесполезно, нужен снимок всей структуры.
- **Поиск** — запрос (линейный проход по титулам, 10³ узлов — микросекунды), а не подписка.

Если когда-нибудь появится второй источник мутаций (плагины, синхронизация файла с диском), оповещение вводится **на границе App**, а не внутри Graph: Graph остаётся «немым» доменным объектом. Это согласуется с рекомендацией преподавателя (сериализация, история команд и алгоритмы развиваются за пределами Graph) и с правилом 21 implementation.md (абстракция поведения угадывается, данные — нет). Синхронность «запрос → ответ» — осознанное ограничение: пока мутация не «долгая», блокирующий вызов из UI проще очереди событий.

### 2.4. Что намеренно НЕ сделано абстракцией

- **`IStorage`** — см. §2.2: граница уже проверяема тестами, второй реализации нет.
- **`GraphSource`** — см. §2.1: отложено до появления второго полного формата.
- **Онтология лент** — конкретная конфигурация, а не стратегия: второй реализации нет и не предвидится.
- **Команды не сериализуются** — живут только в летописи команд (`CommandChronicle`); логирование операций — из перспектив.

## 3. Паттерны проектирования

- **Factory (проверяемая)** — `Graph::FromSnapshot`: единственная точка восстановления модели с валидацией инвариантов (§2.1).
- **Mediator** — *роль слоя App.* Единственная точка, знающая всех участников (UI, Core, Storage): воронка `UI → App → Core ← Storage` вместо прямых связей UI↔Core и UI↔Storage. «Знает всех» здесь — не God Object: у App ноль предметных инвариантов, все решения делегируются; критерий God Object — количество ответственности, а не количество соседей. Знание UI односторонне не выходит: App возвращает данные в ответ на запрос, не вызывая код UI.
- **Observer** — *рассмотрен и отклонён* (§2.3): внешних мутаторов модели нет, обратный поток покрывается синхронными ответами на запросы.
- **Command** — *база реализована (этап 4, implementation.md R14).* Все мутации графа оформляются командами с `Do()/Undo()` (`AnyCommand` = `std::variant` над закрытым набором, концепт `Command` — явный контракт); история — `CommandChronicle` (один вектор + курсор, не два стека). Альтернатива (снапшоты всего графа) проще, но дороже по памяти. Митигация риска: действия канваса (этап 2) с первого дня оформляются командами без истории — тогда этап 4 добавляет только её хранение.
- **Strategy** — *не введён сознательно.* Заменяемых алгоритмов пока нет: раскладка и анализ — отдельные классы клиенты Graph, а не подменяемые стратегии. Если появится вторая реализация раскладки — интерфейс будет введён тогда (YAGNI в обе стороны).
- **Composite** — *проектируемая возможность, в коде не используется.* Общий интерфейс «карта любого уровня вложенности» закладывается под фрактальную вложенность (perspectives.md), но без реального использования вводить его — мёртвый интерфейс.

## 6. SOLID: чек-лист соответствия

Чек-лист — рабочий инструмент ревью: каждый пункт либо «✅ соблюдается» с
доказательством, либо «⚠️ осознанное отклонение» со ссылкой на обоснование,
либо «❌ нарушение → действие». Статусы — на текущее состояние репозитория
(сверено с кодом 2026-10-22; расхождения правились по обе стороны — текст
под код и код под текст).

### SRP — единственная ответственность

- [x] **Ядро не смешивает модель с сериализацией.** `Graph` хранит и валидирует
      состояние; формат файла знает только `JsonStorage`. Граница — DTO
      `GraphSnapshot` (`core/include/graph.hpp`, `storage/include/storage.hpp`).
- [x] **DTO не содержат поведения.** `Node`, `Relation`, `Position`, `NodeType`,
      `RelationType` — только данные + валидация в конструкторе. Дата-классы
      помечены комментарием `// DTO`.
- [x] **Команды — отдельные типы.** `AddNodeCmd`, `DeleteNodesCmd` и др. в
      `app/include/command.hpp` каждая отвечает ровно за одну мутацию.
- [ ] **`JsonStorage::Save` делает две вещи: сериализацию и запись в поток.**
      ⚠️ Допустимо (одна «задача — сохранить сессию»), но если появится
      второй формат (бинарный/экспорт в GraphML) — разнести: `Serialize(snapshot) -> string`
      и запись в поток.
- [ ] **`MainWindow` совмещает маппинг ошибок в строки (`ErrorToString`) и
      координацию сценариев.** ⚠️ Текущий объём (~3,5 КБ, три сценария:
      open/save/save_as) ещё терпим, но при добавлении новых сценариев —
      выносить маппинг ошибок в отдельный модуль/функцию.
- [x] **`NodeItem` читает стиль из `NodeView`.** Раньше: захардкоженный
      `Qt::blue` в `paint()` — нарушение SRP и SSoT (❌). Теперь цвет, форма и
      рамка приходят из онтологии через `NodeView` при создании item'а
      (2026-10-24); `RelationItem` — то же самое для `color`/`arrow`/`symmetric`.
      Скругление честно введено в словарь модели как `rounded_rect`
      (`IsValidShape`, spec §2).

### OCP — открыт для расширения, закрыт для модификации

- [x] **Концепт `Command` + `std::variant` в хронике.** `CommandChronicle`
      работает с любым типом, удовлетворяющим концепту `Command`
      (`command.hpp`), — добавление новой команды не трогает логику undo/redo.
- [x] **Итерация через callback-концепты.** `LiveNodeCallback` / `LiveRelationCallback`
      + `ForEachLiveNode/ForEachLiveRelation` позволяют добавлять алгоритмы,
      не меняя `Graph` (`graph.hpp`). Контракт «не мутировать при итерации»
      зафиксирован в комментарии.
- [ ] **Расширение `AnyCommand` требует правки `command.hpp`** (variant,
      `static_assert`). ⚠️ Осознанно: вариант «type-erasure через
      ICommandInterface» рассмотрен и отклонён в пользу простоты; при росте
      числа команд >8–10 пересмотреть.
- [ ] **`JsonStorage` знает формат целиком; новый `format_version` = правка
      файла.** ❌ Действие: держать версионирование локализованным
      (сейчас так и есть — `kFormatVersion` — не размазывать по коду) и
      документировать правило: «новая версия = новая ветка в `Load`, старая
      не трогается».
- [ ] **Ошибки как `enum class` (`ControllerError`, `CommandError`).**
      ⚠️ Закрыты для добавления нового кода ошибки без перекомпиляции, но
      UI уже содержит `switch` по всем значениям (`MainWindow::ErrorToString`)
      — при добавлении значения enum компилятор не напомнит обо всех местах.
      Действие: добавить `static_assert` на исчерпываемость или `default` с
      метрикой (уже есть `default`, но молчаливый).

### LSP — подстановочность

- [x] **В ядре нет наследования** — LSP нерелевантен по построению
      (композиция + концепты вместо иерархий классов). Это зафиксированное
      архитектурное решение, а не случайность.
- [x] **Иерархия в UI: `NodeItem : QGraphicsObject`, `RelationItem :
      QGraphicsLineItem`.** Обе корректно переопределяют базовые
      виртуальные функции (`boundingRect`, `paint`, `itemChange`) без
      нарушения контрактов Qt; предусловия не усилены.
- [ ] **`operator==` для `double` в `Node::size` и `Position`.**
      ⚠️ Формально нарушение «семантики равенства», но задокументировано
      осознанно (точное сравнение хранимых значений после round-trip; epsilon
      — только для вычисляемой геометрии). Правило: не использовать эти `==`
      для вычисленных координат — только для значений из snapshot.

### ISP — разделение интерфейсов

- [x] **`JsonStorage` — минимальный интерфейс**: два статических метода
      (`Save`/`Load`) + константа версии. Ничего лишнего.
- [x] **Концепты узкие:** `LiveNodeCallback` требует только
      `Fn(const Node&) -> bool`, не тащит в себя зависимостей от `Graph`.
- [ ] **`Graph` — «толстый» интерфейс (~30+ публичных методов).**
      ⚠️ Осознанно: это агрегат корня, тестируемый целиком. Но часть
      поверхности имеет узких владельцев и узкие контракты:
      - `RestoreNodes`/`RestoreRelations` — только undo-стек (владение
        зафиксировано комментарием, enforce — debug-assert); при появлении
        второго потребителя — выносить в отдельный `UndoPort`.
      - `AddNodeWithRelations` — помечен в коде как кандидат на перенос в App
        (композиция не требует доступа к приватному состоянию).
      Действие: не добавлять новых методов с «узким владельцем» в `Graph`
      без отдельного обсуждения.

### DIP — инверсия зависимостей

- [x] **Core не зависит ни от кого** (только STL) — высший уровень не знает
      о низших. Проверяется автоматически: CI-цель `core` собирается без Qt
      (`.github/workflows/ci.yml`).
- [x] **Storage зависит от DTO, а не от `Graph`.** `JsonStorage` работает с
      `GraphSnapshot` — инверсия выполнена правильно (деталь зависит от
      абстракции данных, а не ядро от формата).
- [ ] **UI зависит от конкретного `Controller`.** ⚠️ Приемлемо сейчас
      (один контроллер, headless-тесты `controller_test.cpp` покрывают слой
      без UI). При появлении второго сценария (CLI, скрипты) — ввести
      интерфейс (например, `ISessionCommands`) и инжектировать.
- [ ] **App зависит от конкретного `JsonStorage` (поле в `Controller`).**
      ⚠️ Хорошая новость: API уже опосредован потоками (`istream`/`ostream`),
      так что замена на другой формат — это замена одного поля. При
      добавлении формата: заменить поле на абстракцию сохранения, не
      разрастая `switch`'ами по формату внутри `Controller`.

### Мета-правило чек-листа

- [ ] Каждое отклонение (⚠️) должно ссылаться на основание: ADR, запись в
      `implementation.md` или этот документ. Отклонение без обоснования =
      нарушение.
- [ ] Пункты ❌ не должны пересекать границу релиза: любое ❌ блокирует
      merge, пока не превращено в ⚠️ с обоснованием.

## 7. Инфраструктура: решение и причина

Каждое решение — ответ на конкретный инцидент или риск; «причина» — не
эстетика, а то, что сломалось бы без него. Даты — когда причина впервые
материализовалась.

| Решение | Причина появления |
|---|---|
| CI-матрица core: MSVC/GCC × Debug/Release + clang-cl | Программа отладки ≠ программе релиза, компилятор автора ≠ компилятору CI (implementation.md правила 25, 34); clang-cl — вторая STL/фронтенд на тот же код. Красная Ubuntu-матрица 2026-10-14/17 |
| Санитайзеры ASan+UBSan отдельным job'ом | Ручное индексирование `id − 1` по плотным векторам: off-by-one читается как «работает» на отладочной куче и взрывается у пользователя |
| clang-format 19.1.5 через pip-venv (CI = локальный `.fmt-venv`) | Версии форматируют по-разному: без пина «у меня зелёное, в CI красное» |
| clang-tidy + `.clang-tidy` + `--warnings-as-errors=*`, пин 19.1.0.1 в `.tidy-venv` | Классы ошибок, которые тесты ловят плохо (throw-by-value, неинициализированность, const); гейт держит baseline чистым, пин лечит расхождение версий |
| libFuzzer-таргет `fuzz/` (посев из `examples/`) | Валидация снапшота ручная и длинная — её ломают malformed-входы; property-тесты штатные пути покрывают, мутации — нет |
| Coverage-гейт gcovr `--fail-under-line` | Порог покрытия ратифицирует измеренное, а не желаемое: регресс покрытия виден в CI, а не по ощущениям |
| Архитектурный тест `check_ui_includes.sh` | Инвариант 7 в машинном виде: ui включает только фасад app; срабатывание = сигнал расширить read-API Controller, а не ослабить проверку |
| `include(CTest)` + `add_subdirectory(tests)` без guard `EXISTS` | Пропажа каталога тестов должна ронять configure, а не молча отключать тесты (2026-10-16: перенос tests/ в docs/ выпал из-за guard'а) |
| GoogleTest: `find_package` с FetchContent-фолбэком, пин v1.14.0 | CI без предустановленного gtest; пин тега — воспроизводимость |
| `RAVEL_REPO_ROOT` для тестов на golden-файлы | cwd бинаря при запуске ctest не гарантирован — тесты должны находить `examples/` из любого каталога |
| Сохранение через temp-файл + `rename` | Краш посередине записи не должен оставлять битый файл на месте целевого |
| `.editorconfig` | Единый стиль концов строк/отступов между VS, VS Code и прочими редакторами — формат-гейт ловит C++, но не JSON/доки |
