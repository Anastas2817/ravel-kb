# Архитектура

## 1. Слои

```
┌─────────────────────────────────────────────┐
│  UI (Qt 6 Widgets)                          │
│  QGraphicsView / QGraphicsScene             │
├─────────────────────────────────────────────┤
│  Приложение                                 │
│  команды (Command + undo/redo),             │
│  контроллеры, история                       │
├─────────────────────────────────────────────┤
│  Ядро (чистый C++17, без зависимостей от Qt)│
│  Graph · SugiyamaLayout ·                   │
│  OntologyLanes · PageRank (позже)           │
├─────────────────────────────────────────────┤
│  Хранение (IStorage)                        │
│  JsonStorage                                │
└─────────────────────────────────────────────┘
```

Ключевое правило: **ядро не зависит от Qt**; UI зависит от ядра, но не наоборот. Замена реализации любого слоя не затрагивает соседние.

### 1.1. Почему ядро без Qt

Обоснование — не эстетика «чистоты», а измеримые выгоды:

1. **Тестируемость без GUI.** Все тесты ядра (инварианты модели, round-trip сериализации, раскладка, команды) запускаются headless: без оконного сервера, без Qt вообще. Сборка и прогон тестов ядра занимают секунды, а не минуты.
2. **CI дешевле и надёжнее.** CI-цель `core` собирается и тестируется без установленного Qt — меньше зависимостей, меньше шанс сломать сборку из-за окружения. Qt-сборка проверяется отдельной целью.
3. **Дисциплина зависимостей.** Запрет Qt в ядре — автоматическая проверка границ слоёв: если для фичи «нужно немного Qt в core», это сигнал, что фичу спроектировали неверно (логика утекла в presentation).
4. **Переносимость и переиспользование.** Ядро — статическая библиотека; потенциально собирается под любую платформу и может быть переиспользовано вне десктопного UI (CLI-утилиты, тестовые генераторы, будущие бэкенды из перспектив).

Ядро использует только стандартную библиотеку C++17.

## 2. Ключевые абстракции

| Интерфейс / класс | Назначение | Реализация |
|---|---|---|
| `ILayoutAlgorithm` | раскладка графа | `SugiyamaLayout` |
| `IStorage` | сериализация | `JsonStorage` |
| `Command` | мутации графа с откатом | `AddNodeCmd`, `AddEdgeCmd`, `MoveNodeCmd`, … |
| `GraphObserver` (собственный) | события ядра для внешних подписчиков | адаптер в UI превращает в Qt-сигналы |

Ниже — честное обоснование каждой абстракции: зачем нужна и чем бы её можно было заменить.

### 2.1. ILayoutAlgorithm

**Зачем.** Раскладка оперирует только моделью (`Graph` + онтологией) и возвращает координаты — ей не нужен ни экран, ни виджеты. Интерфейс позволяет: (1) тестировать раскладку на синтетических графах без GUI; (2) подставлять в тестах no-op/«наивную слоистую» реализацию для изолирования UI; (3) в будущем сравнивать алгоритмы и бенчмаркать (см. метрики roadmap).

**Честная оговорка.** Сегодня реализация одна, и интерфейс — это прежде всего точка тестирования и демонстрация паттерна Strategy, а не горячая потребность. Стоимость поддержки интерфейса низкая (один класс, чистая семантика), поэтому оставляем; если реализация навсегда останется одной — интерфейс можно будет удалить без потерь (YAGNI работает в обе стороны).

### 2.2. IStorage

**Зачем.** Сериализация — чистый ввод-вывод, который (1) тестируется round-trip тестами через подменную реализацию в памяти, (2) изолирует зависимость от конкретной библиотеки JSON (nlohmann/json подтягивается через FetchContent и подменяема), (3) оставляет дверь открытой для альтернативного бэкенда (графовая СУБД, см. perspectives.md) без переписывания приложения.

Это самый оправданный интерфейс проекта: граница «модель ↔ байты на диске» тестируется напрямую.

### 2.3. Command

**Зачем.** Undo/redo требует, чтобы каждая мутация знала, как откатить себя. Единая иерархия `Command` с `do()/undo()` даёт: (1) стеки undo/redo как простую структуру над однотипными объектами; (2) единственную точку изменения состояния графа (инвариант, проверяемый в review и тестами); (3) тест «do → undo → состояние совпадает с исходным» в одном месте для всех команд.

Альтернатива — снапшоты всего графа — проще, но дороже по памяти и не масштабируется до лога операций.

### 2.4. Собственный Observer (а не std::function и не Qt-сигналы)

**Почему не Qt-сигналы:** ядро не может зависеть от Qt (§1.1).

**Почему не «голый» `std::function` в каждом подписываемом месте.** Интерфейс рассыльщика (`Signal<T>` в ядре) даёт то, что `std::function` не даёт из коробки:

1. **Множественные подписчики** с явной отпиской: возвращается токен подписки (RAII-handle), отписка при уничтожении подписчика — без ручного контроля жизненного цикла «кто какой колбэк держит».
2. **Именованные каналы событий** (`node_added`, `edge_removed`, …) вместо размножённых по классам полей-колбэков — события ядра видны в одном месте API и тестируются шпионами-подписчиками.
3. **Тестируемость:** тест ядра подписывается на сигнал и проверяет, что событие пришло, — без UI и без Qt.

`std::function` достаточен для одиночного колбэка «состояние изменилось» у конкретного объекта; для событийной модели ядра (много источников × много подписчиков × контролируемая отписка) собственная реализация «сигнал/слот» дешевле и безопаснее. Адаптер в UI-слое превращает сигналы ядра в Qt-сигналы виджетов.

### 2.5. Что намеренно НЕ сделано интерфейсом

- **Онтология секторов/лент** (`OntologyLanes`) — конкретный класс, конфигурация, а не стратегия: второй реализации нет и не предвидится, замена конфигурацией покрывает сценарий «другая дисциплина». Вводить `ISpatialSemanticsResolver` до появления второй реализации — преждевременная абстракция.
- **Команды не сериализуются** — только в стеках undo/redo; макросы/логирование операций — из перспектив.

## 3. Паттерны проектирования

- **Strategy** — заменяемые алгоритмы раскладки и хранения через интерфейсы (§2.1, §2.2).
- **Command** — все мутации графа оформляются командами с `do()/undo()`; история хранится в стеках undo/redo (§2.3).
- **Observer** — собственная легковесная реализация «сигнал/слот» в ядре (§2.4).
- **Composite** — *проектируемая возможность, в текущей реализации не используется.* Граф и мини-карта должны реализовать общий интерфейс, чтобы оперировать картой любого уровня вложенности единообразно (закладывается в API под фрактальную вложенность, perspectives.md §1). В код MVP закладывать не будем: без реального использования это мёртвый интерфейс.

## 4. Инварианты модели

- Рёбра ссылаются только на существующие узлы.
- Идентификаторы узлов и рёбер уникальны и не переиспользуются.
- Тип каждой связи и узла должен существовать в словаре типов.
- Все мутации графа выполняются через команды (единственная точка изменения состояния).
- Инвариант «алиас не может ссылаться на узел-предок» относится к алиасам и действует с момента их появления (perspectives.md §3).
