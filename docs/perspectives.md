# Проектируемые возможности (перспективы)

> **Этот файл — развитие за пределами курсовой, но не всё здесь «мечта».** §1 — зафиксированная боль текущего инструмента и приоритет №1 после вехи «свой конспект» (roadmap.md); остальные разделы — направления, не являющиеся планом на ближайшие итерации. Порядок примерно отражает приоритет, но не обязателен.

## 1. Фрактальная нотация (вложенность карт)

**Статус: боль, а не мечта.** В ExcaliBrain, текущем инструменте автора, структура «большой» заметки не помещается в её окрестность на общей карте; обход — Ctrl+M: заметка превращается в отдельный холст, и её структура строится заново, вручную. Это повторяющийся ручной обход отсутствия вложенности — та самая боль, которую убирает фрактальная нотация.

**Определение.** Фрактальный узел — узел, раскрывающийся в отдельную мини-карту. На родительской карте его связи с внешними понятиями кодируются составной нотацией:

```
[ <фрактал> → <внутренний_узел> ]
```

где `<фрактал>` — имя фрактального узла, `<внутренний_узел>` — понятие, существующее на мини-карте, `→` — направление связи (возможны `←`, `↔`), `[ ... ]` — общий прямоугольник-контейнер, визуально объединяющий обе метки.

Теоретическая база — *compound digraphs* у Sugiyama & Misue (см. spec.md §2.2).

**Правила отрисовки**

1. На родительской карте связь фрактала с внутренним узлом рисуется как один прямоугольник с двумя метками, разделёнными стрелкой.
2. Прямая стрелка между фракталом и внешним узлом не проводится — связь существует только через раскрытие мини-карты.
3. Внутри мини-карты связь может быть не прямой: путь проходит через промежуточные узлы (цепочка, цикл, ветвление).
4. Контейнер наследует цвет типа связи; метки внутри сохраняют цвет своих типов узлов.

**Пример.** На родительской карте: `[ Фракталы → Множество Кантора ]`. Внутри мини-карты «Фракталы» путь может быть: `Фракталы → Самоподобие → Канторово множество → Множество Кантора`.

**Семантика.** Нотация читается как «Фракталы связаны с Множеством Кантора через внутреннюю структуру мини-карты». Это не прямое ребро, а свёрнутый путь — визуальная абстракция, скрывающая детали до раскрытия. Для алгоритмов анализа графа связи на мини-картах не учитываются.

## 2. Призрачные альтернативы иерархии

Один и тот же граф допускает несколько равноправных иерархий в зависимости от задачи и доминирующего типа связи: раскладка по `is_a` и раскладка по `has_part` дают разные, но одинаково осмысленные картины. Реализация — как альтернативные раскладки одного множества узлов и связей (view, не копия модели данных). Пользователь переключается между ними; на фоне отображается фигура-контейнер, объединяющая альтернативы, клик раскрывает выбор. Уровни: (A) переключение через меню по доминирующему типу связи; (B) выбор в UI с сохранением последнего состояния; (C) фигура-контейнер и визуальное сравнение.

## 3. Ссылочные узлы (алиасы)

Для уменьшения «шума» на перегруженных картах узел может быть показан в нескольких местах:

- **Алиас** — визуальная копия узла с пунктирной рамкой и меткой-ссылкой; клик переносит к оригиналу. Алиас занимает одну позицию в текущей карте, но не дублирует данные и не влияет на метрики (PageRank, степень).
- Алиас, ссылающийся на узел-предок в той же карте, запрещён (инвариант: навигационные циклы невозможны).
- Форма узла кодирует статус: прямоугольник — оригинал, пунктирный — алиас. Цвет остаётся кодом типа.

## 4. Топ-N отображение связей

При числе связей узла более N отображаются приоритетные связи (ранжирование по типу и степени соседей), остальные — по явному запросу («показать все»). Полнота не жертвуется, а прячется за действием пользователя (принцип «читаемость важнее полноты», spec.md §1).

## 5. Метаузлы для перегруженных областей

Когда сектор окрестности узла превышает порог N, система предлагает сгруппировать часть соседей в метаузел — узел-агрегат, раскрываемый по клику. Вручную или автоматически — только по решению пользователя.

## 6. Прочее (по мотивам roadmap хвоста)

- Симметричные типы связей: горизонтальная отрисовка внутри слоя (в текущей раскладке симметричные типы просто не создают иерархии).
- PageRank для размера узлов (замена степени).
- «Выпрямление» длинных рёбер в Сугияме (dummy-узлы).
- **Слияние параллельных рёбер и hierarchical edge bundling.** Визуальное смягчение межленточных пересечений (fading и hover-подсветка) входит в MVP (roadmap.md, этап 3c). Следующий шаг — слияние параллельных рёбер в общий путь: два ребра, идущих из одной окрестности в другую, рисуются как один «ствол» нейтральным цветом, ветвящийся у концов в цвета типов. Это решает проблему «=>—>», но требует отдельного слоя отрисовки поверх раскладки. Полноценный hierarchical edge bundling (Holten) — исследовательская задача, не для MVP.
- UI-редактор словаря типов связей и пользовательской онтологии (сектора, ленты).
- Графовая СУБД (Kuzu) как альтернативный бэкенд через `IStorage`.
- LLM-предложение связей (link prediction) по окрестности узла — **строго опциональные подсказки, не извлечение из текста и не автоматическое построение графа**.
- Плагин для Obsidian.
- Бенчмарк раскладки (графы 10²–10³ узлов), оценка сложности.

## 7. LaTeX-формулы в узлах

**Боль.** Для математических дисциплин название и описание узла без формул почти бесполезны. Сейчас формулы живут в заметках Obsidian рядом с картой — карта не самодостаточна, а ExcaliBrain решает это только локально, внутри одной заметки.

**Технические варианты (по возрастанию тяжести):**

1. **Оффлайн-рендер в SVG.** Формулы (`$...$`) в описании при редактировании рендерятся через MathJax (CLI) или системный TeX → dvisvgm; SVG кэшируется и отображается через `QSvgRenderer`/`QGraphicsSvgItem`. Исходник LaTeX остаётся в описании — поиск, git-diff и редактирование работают с текстом. Плюс: нет тяжёлых зависимостей в рантайме. Минус: нужен node или TeX на машине пользователя — проблема распространения; выход — опциональная зависимость: без неё формула показывается исходным текстом.
2. **Qt WebEngine для панели описания** — MathJax/KaTeX как в Obsidian. Качество рендера и редактирование уровня Obsidian, но WebEngine — гигантская зависимость (память, размер установки) для десктопного приложения.
3. **Собственный рендерер подмножества LaTeX** на QPainter. Ноль внешних зависимостей, но подмножество будет маленьким и багованным — для математической аудитории тупик.

**Рекомендация.** Вариант 1 с опциональным MathJax CLI. Не входит в MVP: до вехи «свой конспект» формулы можно держать в описании исходным текстом — раскладке и связям это не мешает.

## 8. Эскизы узлов (поле рисования)

**Идея.** Понимание часто приходит картинкой быстрее, чем словом: схема, черновик доказательства, диаграмма. Отдельное поле-эскиз у узла позволяет фиксировать мысль в момент создания узла — без открытия редактора заметок и без формулировки текста.

**Почему отдельное поле, а не часть описания.** Описание остаётся текстом: поиск, git-diff и round-trip работают на тексте. Бинарное изображение внутри описания разрушило бы версионируемость и человекочитаемость файла.

**Хранение.** Отдельный файл на эскиз (`assets/node_<id>.png`), в JSON — только флаг/путь. Вариант «base64 в JSON» отвергнут: раздувает файл и ломает git-diff. При копировании узла между файлами эскиз копируется под новым id целевого файла (согласовано с правилами переноса id, spec.md §4.2). При удалении узла эскиз удаляется каскадно; команда удаления сохраняет его для undo.

**Интеграция.** Замена эскиза — одна команда (undo/redo, как для текста). На узле — индикатор наличия эскиза (уголок/иконка). Мини-редактор — простейший холст на QGraphicsView, независимый от основного канваса.

**Границы.** Эскиз — не замена LaTeX (§7): эскиз это быстрый нечёткий путь «как пришло в голову», LaTeX — точный. Полноценный растровый редактор (слои, стили, импорт) — за пределами: Ravel не графический редактор.

## 9. Мнимые узлы (инкубатор)

**Статус: идея-гипотеза.** Не боль, не мечта: проверка того, что отложенная типизация помогает не терять мысль, а не только ускоряет уже принятое решение (ср. §4.1 spec).

**Определение.** Мнимый узел — узел без типа и без типизированных связей. Он не существует на карте: не участвует в раскладке, не влияет на метрики, не виден в графе. Живёт «в другом измерении» — в отдельном хранилище черновиков, к которому карта обращается только тогда, когда мнимый узел готов стать настоящим.

**Материализация.** Мнимый узел появляется на карте ровно в тот момент, когда указаны все типы: собственный тип узла и типы всех его связей. До этого момента он — мысль, зафиксированная в моменте: название и описание, без обязательства решить, `is_a` это или `has_part`.

**Зачем.** Три механизма снижения цены типизации (§4.1 spec) уменьшают *стоимость* решения. Мнимый узел решает другую задачу — снимает его *срочность*. Мысль, пришедшая в голову в момент, когда некогда думать о типе связи, не теряется и не заставляет бросать текущее дело.

**Почему «мнимый», а не «черновой».** «Черновой» звучит как недо-узел, временное состояние того же самого. Мнимый — принципиально другая сущность: он в другом пространстве, он не «почти на карте», он вне её. Материализация — не «доделывание», а переход между измерениями.

**Что заставляет разобрать очередь.** Мнимый узел не виден на карте — и это его главное свойство. Карта, в которой чего-то не хватает, вызывает желание это исправить; если желания нет — мысль не была достаточно ценной, чтобы за неё держаться, и очередь сама рассасывается. Это не наказание за лень, а естественный фильтр: очередь из мнимых узлов — видимая мера того, сколько ещё не понято.

**Автоматика только советует.** Мнимые узлы — не повод для исключения из принципа. Три роли системы:

1. **Показать очередь.** Счётчик в статус-баре («3 мнимых узла ждут типизации»), список в боковой панели. Без видимости очередь превращается в кладбище — это критично.
2. **Предложить контекст.** При материализации — тип по онтологии концов (§4.4 spec): для пары function → model — `is_defined_on`. Ровно тот же механизм, что и для обычных связей.
3. **Мягко напомнить.** «Мнимых узлов больше, чем настоящих — возможно, стоит разобрать очередь». Рекомендация, не блокировка.

Система никогда не материализует мнимый узел сама, не угадывает тип и не удаляет забытые черновики по таймауту.

**Хранение.** В том же JSON-файле, отдельной секцией (`draft_nodes`), с бампом `format_version`. Вынос во внешнее хранилище отвергнут: round-trip, git-diff и переносимость файла должны работать как для остального содержимого. id мнимого узла — из того же `next_id` (единое пространство, spec §4.2); при материализации id не меняется, чтобы ссылки в других черновиках не ломались.

**Открытые вопросы (до реализации):**

- Может ли мнимый узел ссылаться на реальные узлы карты? Если да — что при удалении целевого узла: черновик помечается битым, предлагается перепривязать или удалить.
- Можно ли вернуть материализованный узел в мнимое состояние («передумал, ещё не готов»)? Логично разрешить, но это отдельная команда.
- Создание, редактирование и материализация мнимого узла — через Command, иначе undo/redo не переживёт черновики.

**Границы.** Мнимый узел — не «отложенная связь» и не «временный тег». Если пользователь заводит 200 мнимых узлов и 50 настоящих — он вернулся к тому, от чего ушёл: структура не построена, решения отложены. Это не аргумент против механизма, но аргумент за то, что видимость очереди обязательна, а не опциональна.
