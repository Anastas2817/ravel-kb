# Исследовательская программа: типизированная метрика графа и семантическая проекция

> **Статус: исследовательская рамка за пределами MVP курсовой.** Этап A (метрика + взвешенная раскладка) реализуем в рамках ядра сразу после MVP; этапы B–C — после вехи «свой конспект» (roadmap.md). Этот документ — постановка задач, а не план фич; код пишется отсюда.
>
> **Честная рамка.** Gärdenfors (spec.md §2.2) — философское обоснование: карта как проекция смыслового пространства. Формальное ядро здесь — скромнее и честнее: **взвешенная метрика типизированного графа** и её проекция с дискретными ограничениями. Это не концептуальное пространство в строгом смысле Гёндерфорса (у нас нет непрерывных измерений качеств — только структура графа); ссылка на conceptual spaces — мотивация, а не формальная база. Так и пишем в любой работе.

## 1. Объекты и обозначения

- Типизированный ориентированный граф `G = (V, E, T)`, `T` — словарь типов связей со свойствами из spec.md §4.2 (`symmetric`, `transitive`).
- Вес типа: `w: T → R>0`. **Смысл: меньший вес = более тесная связь = меньшее расстояние.**
- Иерархические типы (`is_a`, `has_part`, …) задают слои; онтология задаёт ленты (spec.md §5.1) — как и сейчас, это вне метрики.

## 2. Типизированная метрика (этап A)

**Определение (взвешенное путевое расстояние).**

```
d(u, v) = min over paths p: u → v of Σ_{e ∈ p} w(type(e))     (∞, если пути нет)
```

**Свойства и их следствия.**

- `d` удовлетворяет неравенству треугольника (взвешенные кратчайшие пути); `d(u,u)=0`; при всех `w > 0` положительная определённость. Это метрика в обычном смысле — на этом держится вся дальнейшая конструкция.
- **Транзитивность не требует замыкания графа.** Цепочки транзитивного типа учитываются метрикой сами: расстояние по `is_a` — это длина цепочки обобщения. Это свойство важно: модель не раздувается производными рёбрами (spec.md §5.3 остаётся в силе).
- **Несимметричность.** Для ориентированных типов `d(u,v) ≠ d(v,u)`. Проекции (§3) и подсказкам (§5) нужна симметричная мера → рабочее определение `s(u,v) = (d(u,v) + d(v,u)) / 2`. Вариант `min` — открытый вопрос (§7).
- **Несвязные узлы**: `d = ∞`. Рабочее правило: подсказки строятся только внутри компоненты связности (карты персональны и малы — компонента почти всегда одна; проверка дешёвая).

**Стартовые веса (гипотеза, не константы).**

| Тип | w | Обоснование-гипотеза |
|---|---|---|
| `isomorphic_to` | 0.6 | Самая тесная связь: «одно и то же в другом обличье» |
| `is_a` | 1.0 | Тесная иерархическая |
| `has_part` | 1.1 | Иерархическая, чуть слабее обобщения |
| `is_defined_on`, `is_model_of` | 1.5 | Контекстные связи, слабее иерархических |
| пользовательские | 1.5 | Дефолт до калибровки (этап B) |

Гипотеза, которую проверяем: иерархические типы должны давать заметно меньшие расстояния, чем контекстные, иначе метрика вырождается в «всё равно всё связано со всем». Контрольная проверка на демонстрационной базе: гистограмма `s(u,v)` по всем парам не должна быть вырождена в пик у минимума.

**Сложность.** Для 10³ узлов: Флойд–Уоршелл — ~10⁹ операций над матрицей 8 МБ, порядка секунды; Dijkstra от каждого узла — быстрее на разреженных картах. Метрика считается не на каждую правку, а по запросу (кнопка «Пересчитать метрику» / перед пакетом подсказок) и кэшируется с инвалидацией по изменению графа. Полное обоснование лимита 10³ — появляется здесь, в research-рамке.

## 3. Семантическая проекция: раскладка как ограниченная оптимизация (этап A)

**Дискретные ограничения (фиксируются до оптимизации).** Слой `L(v)` — из иерархических типов (как в spec.md §5.1); лента `S(v)` — из онтологии. Перестановки, нарушающие ленты, запрещены — перенос принципа spec.md §5.2 на новый критерий.

**Непрерывные переменные.** Горизонтальная координата внутри ленты `x(v) ∈ R`. Вертикаль внутри слоя — фаза назначения координат (Brandes–Köpf / priority method, roadmap.md, этап 3b), метрикой пока не управляем.

**Целевая функция (взвешенное рассогласование).**

```
minimize  Σ_{(u,v) ∈ E, S(u) = S(v)}  w(type(u,v)) · (x(u) − x(v))²
          по x, при фиксированных L, S и запрете перестановок между лентами
```

Оптимум по `x(u)` при прочих фиксированных: `x(u) = Σ w·x(v) / Σ w` — **взвешенный барицентр**. Следствие, связывающее исследование с текущим планом: **один проход классических барицентров — это один шаг координатного спуска по этой целевой функции при равных весах.** Этап 3a roadmap.md — частный случай этапа A при `w ≡ 1`. Модифицированный Сугияма Ravel — не отбрасывается, а получает весовое обобщение; это и есть формальная «зацепка» проекта.

**Пересечения — вторичный критерий.** Минимум рассогласования не гарантирует минимум пересечений: после спуска по рассогласованию остаётся жадная фаза уменьшения пересечений внутри лент (как сейчас). Исследовательский вопрос — величина конфликта критериев на реальных картах (§7).

**Межленточные рёбра.** В целевую функцию не входят (свободы нет), как и сейчас (spec.md §5.2): смягчаются визуально, а их метрическая роль реализуется через метрику, а не через координаты.

**Место в архитектуре.** Новая реализация `ILayoutAlgorithm` — `WeightedBarycenterLayout` (наследник `SugiyamaLayout`, spec.md §5.1 → стратегия из architecture.md §2.1 получает вторую реализацию — интерфейс перестаёт быть преждевременной абстракцией). Модуль `core/metric` (чистый C++17, тестируется headless).

## 4. Калибровка весов (этап B, после вехи «свой конспект»)

**Данные.** Естественные сигналы пользователя, без отдельного аннотирования:

1. accept/reject подсказок link prediction (этап C работает до калибровки на стартовых весах — данные копятся с первых подсказок);
2. ручные переопределения позиций (spec.md §5.5): пара узлов, поставленных рядом вручную, — положительный пример малого `s`; удаление подсказанной связи — отрицательный.

**Модель (намеренно предельно простая).**

```
P(связь типа t между u и v) = σ( a_t − b_t · s(u,v) ),   b_t > 0
```

Логистическая регрессия с единственной фичей — расстоянием. Интерпретируемость обязательна: подсказка всегда сопровождается объяснением («близко через `has_part`: путь X → Y → Z»), коэффициенты читаются как «какой тип связи на каком расстоянии правдоподобен».

**Обучение.** Градиентный шаг по принятым/отклонённым парам, с регуляризацией к стартовым весам (малые данные — штраф за отдаление от гипотезы §2). Это **калибровка эвристики, а не машинное обучение в серьёзном смысле** — при 10² событиях честнее так и называть. Тяжёлые модели (градиентный бустинг, эмбеддинги TransE/RESCAL-типа) — за пределами: осмысленны от ~10⁴ триплетов, наш масштаб — 10³ узлов.

## 5. Link prediction без LLM (этап C)

**Нулевой слой — логический вывод, не предсказание.** Транзитивные типы: наличие пути `u →is_a … →is_a v` даёт логически гарантированную неявную связь. Показываем отдельно от предсказаний (пометка «вывод», не «подсказка»).

**Скоринг кандидатов.**

```
score(u, v, t) = −s(u,v) + λ · prior(t | type(u), type(v))
```

- кандидаты: k ближайших к u по `s` внутри компоненты связности;
- `prior(t | типы концов)` — частотная таблица по текущей карте (spec.md §4.4: онтология концов уже предлагает тип — это тот же механизм, метрика добавляет ранжирование);
- λ — параметр, при λ → ∞ вырождается в текущее поведение §4.4 (дефолтный безопасный режим).

**Принципиальные ограничения** (spec.md §3 не-цели не нарушаются): только подсказки, никогда автоматическое создание; объяснение обязательно; отклонённые подсказки уходят в данные этапа B.

**Валидация.**

- Hold-out: 20 % рёбер, стратифицированно по типу, 5 разбиений;
- метрики: AUC-ROC и Hits@10, по типам и в среднем;
- базовые линии, которые обязаны побить: случайное предсказание, частотный prior (λ → ∞), common-neighbors. Если метрика не бьёт частотный prior — честный отрицательный результат: метрика не несёт сигнала, веса гипотеза неверна, документ обновляем;
- на личной базе 10²–10³ узлов интерпретировать как качественную оценку, не как строгий эксперимент.

## 7. Открытые вопросы

1. `s = среднее` vs `s = min` для несимметричных типов — решить на данных демонстрационной базы.
2. Величина конфликта «рассогласование vs пересечения»: измерить на 5–10 реальных картах (счётчик пересечений уже в метриках roadmap.md).
3. Входят ли симметричные типы в метрику с весом 0.6 или исключаются (spec.md §5.3: иерархии не создают — но метрика не про иерархию)? Дефолт: входят.
4. Нужна ли метрике вертикаль (внутрислойные y при priority method) или горизонтали достаточно — вопрос фазы 3b.
5. Поведение кэша метрики при undo/redo: пересчёт или откат кэша? (Командная модель позволяет версионировать кэш — выбрать по профилированию.)
