# Обоснование выбора технологий (tech stack)

Документ фиксирует, **почему** выбраны C++23, Qt 6 Widgets, nlohmann/json и
сопутствующая инфраструктура. Обоснование строится сначала от требований ([c1_scope.md](c1_scope.md),
[spec.md](spec.md) §7, [architecture.md](architecture.md) §1, §4).

## 1. Требования, из которых следует стек

| # | Требование | Источник | Что оно диктует |
|---|---|---|---|
| R1 | Десктопное, офлайн, single-user приложение; нет сети, облака, коллаборации | c1_scope §1, §2, §7 | Не нужен веб-стек, серверная часть, рантайм браузера; ценность — нативность и предсказуемость |
| R2 | Файл — человекочитаемый JSON, версионируемый через git | c1_scope §3, §5 | Детерминированная сериализация; парсер с понятными ошибками; «отклонить с понятной ошибкой» — часть SLA |
| R3 | Семантическая раскладка (модифицированный Сугияма + онтологические ленты) — ядро ценности | c1_scope §5, spec §1 | Геометрические алгоритмы на графе: производительность и детерминизм важнее скорости разработки фич |
| R4 | Advisors: свет/тень/градиенты как грамматика подсказок, бюджет движения, custom painting | advisors.md | Нужен низкоуровневый контроль отрисовки (paint), а не декларативные анимации |
| R5 | ~10³ узлов; пересечения рёбер — O(E²) один раз после раскладки, с кэшем | c1_scope §8 | Умеренная нагрузка, но латентность раскладки должна быть интерактивной; ручные позиции поверх |
| R6 | Корректность важнее скорости; инварианты модели; валидация снапшота | c1_scope §8, architecture §2.1 | Статическая типизация, проверки на этапе компиляции, санитайзеры, фаззинг |
| R7 | Windows / Linux; MSVC 2022 и GCC в CI | c1_scope §8, README | Кроссплатформенный тулчейн без «платформенного» кода в ядре |
| R8 | Undo/redo через Command; один разработчик | c1_scope §5, §7 | Компактность кодовой базы, низкая стоимость владения, отладка end-to-end |

## 2. Критерии выбора

1. **Соответствие требованиям** — технология закрывает конкретное требование из §1, а не «модно».
2. **Предсказуемость** — детерминированная латентность и память (R3–R5), воспроизводимые сборки и форматирование.
3. **Стоимость владения для команды из одного человека** — честно: время отладки и скорость обучения важнее гипотетических экосистемных выгод. Для single-user офлайн-приложения «экосистема PKM на JS» (синхронизация, плагины, коллаборация) закрывает требования, которых у Ravel нет (R1).
4. **Проверяемость** — каждое решение должно выдерживать машинную проверку в CI (санитайзеры, fuzz, архитектурный тест), а не только слова.

## 3. Язык: C++23

**Закрывает:** R3, R5, R6, плюс R8 (компетенция команды).

- **Вычислительное ядро — раскладка и анализ.** Модифицированный Сугияма,
  DFS, PageRank, подсчёт пересечений (R3, R5) — это плотная работа со
  структурами данных в куче. C++ даёт value semantics, RAII и отсутствие
  пауз сборщика мусора — латентность раскладки и отрисовки advisors
  детерминирована и измерима, без GC-всплесков в середине жеста.
- **Модель ошибок `std::expected` (C++23).** Контракт команд —
  `CommandResult = std::expected<void, CommandError>` (command.hpp): ошибочный
  путь невозможно проигнорировать, исключения через слои не летят.
  `UnknownType` / `EntityGone` / `QuotaExceeded` зарезервированы под границу
  Controller'а — единственную точку перевода исключений Graph в результат для
  UI (implementation.md R14). Это прямое воплощение требования R2/R6
  «отклонить с понятной ошибкой» в типах.
- **`concept` как контракт вместо иерархий.** `CommandChronicle` принимает
  любой тип, удовлетворяющий концепту `Command`; `AnyCommand` — закрытый
  `std::variant` над ними (architecture §3, OCP-пункт чек-листа). Добавление
  команды не трогает логику undo/redo — расширение без модификации
  проверяется компилятором, а не ревью.
- **Язык + тулчейн = единая система гарантий.** `/permissive-`, `-Werror`,
  ASan/UBSan, libFuzzer, clang-tidy — дешевы именно потому, что весь стек
  один: нет «второго рантайма» для отладки (см. §7 о QML).
- **Честное замечание.** C++23 — основной язык команды. Для проекта с одним
  разработчиком это не антиаргумент, а критерий риска: язык, в котором
  разработчик мыслит, снижает вероятность архитектурных ошибок сильнее,
  чем гипотетическая продуктивность незнакомого стека. Это зафиксировано,
  а не скрыто.

## 4. UI: Qt 6 Widgets

**Закрывает:** R1, R4, R7.

- **Канвас — это `QGraphicsScene/View`.** Требования канваса (R3, R4,
  c1_scope §5): перемещаемые узлы, рёбра вслед за драгом, создание связи
  жестом, цветовое кодирование по типам, ручные позиции. QGraphics*
  предоставляет именно это: item-based сцена, `itemChange`, `paint()` с
  полным контролем кисти.
- **Advisors — paint-уровень, не декларативные анимации.** Грамматика
  света (advisors.md §1–2): свечение, тень, температурный градиент,
  пульс — это эффекты, рисуемые в `paint()` с точным контролем бюджета
  движения. Qt Widgets даёт прямой доступ к `QPainter`; QML/JS-конвейер
  анимаций здесь был бы прослойкой между замыслом и пикселем.
- **Один язык на все этажи.** UI на Widgets — тот же C++: один дебаггер,
  один стек вызовов от жеста до мутации модели, без JS-движка и
  компиляции QML в рантайме. Для R8 (один разработчик) это низкая
  стоимость end-to-end отладки.
- **Правило «ядро без Qt» становится проверяемым.** Требование «UI → App →
  Core ← Storage» (architecture §1) при Qt=C++ родном языке UI превращается
  в машинный тест `check_ui_includes.sh`: ui включает только фасад app.
  Смешение языков (C++ ядро + JS/QML UI) эту границу размывало бы.
- **Нативный десктоп без упаковки браузера.** R1: single-user офлайн —
  ценность в нативности, доступности, низком потреблении. Электрон-подобный
  стек тащил бы рантайм браузера ради приложения без сети.
- **Честная цена.** Widgets уступает QML в дизайнерской итерации и
  «современном» виде по умолчанию; это осознанно принято: визуальный язык
  Ravel строится кастомной отрисовкой (R4), а не шаблонными контролами.

## 5. Сериализация: nlohmann/json

**Закрывает:** R2, R6, R8.

- **Формат — требование, а не следствие библиотеки.** c1_scope §3: файл —
  единственный носитель состояния, читаем человеком, версионируется git.
  nlohmann/json даёт детерминированный `dump` (стабильный порядок ключей →
  чистые диффы) и ошибки парсинга с позицией — «понятная ошибка» из
  c1_scope §8 буквально.
- **Хранилище остаётся Qt-free.** Альтернатива в лице `QJsonDocument`
  утащила бы сериализацию в GUI-фреймворк: тесты storage'а потребовали бы
  Qt-стека, нарушив решение architecture §1.1 (ядро и хранилище — чистый
  C++23) и усложнив CI (`RAVEL_BUILD_UI=OFF` собирает всё без Qt).
- **Header-only + FetchContent.** Зависимость подтягивается одной строкой
  CMake с пином версии; нет системных пакетов и второго пакетного менеджера.
- **Почему не альтернативы.** RapidJSON быстрее, но нагрузка у Ravel — не
  пропускная способность парсера, а валидация: `Graph::FromSnapshot` сам
  разбирает семантику (architecture §2.1), парсеру нужны точность ошибок,
  а не микросекунды. boost.json — более тяжёлая зависимость без выигрыша
  в нужном свойстве.
- **Дружественен фаззингу.** Публичный парсинговый API — удобная мишень для
  libFuzzer-таргета `fuzz/` (см. §6): malformed-входы ломают именно
  ручную валидацию снапшота, которую штатные тесты не достают.

## 6. Инфраструктура: решение и причина

Каждое решение — ответ на конкретный инцидент или риск; «причина» — не
эстетика, а то, что сломалось бы без него. Даты — когда причина впервые
материализовалась. (Перенесено из architecture.md §7.)

| Решение | Причина появления |
|---|---|
| CI-матрица core: MSVC/GCC × Debug/Release + clang-cl | Программа отладки ≠ программе релиза, компилятор автора ≠ компилятору CI (implementation.md правила 25, 34); clang-cl — вторая STL/фронтенд на тот же код. Красная Ubuntu-матрица 2026-10-14/17 |
| Санитайзеры ASan+UBSan отдельным job'ом | Ручное индексирование `id − 1` по плотным векторам: off-by-one читается как «работает» на отладочной куче и взрывается у пользователя |
| clang-format 19.1.5 через pip-venv (CI = локальный `.fmt-venv`) | Версии форматируют по-разному: без пина «у меня зелёное, в CI красное» |
| clang-tidy + `.clang-tidy` + `--warnings-as-errors=*`, пин 19.1.0.1 в `.tidy-venv` | Классы ошибок, которые тесты ловят плохо (throw-by-value, неинициализированность, const); гейт держит baseline чистым, пин лечит расхождение версий |
| libFuzzer-таргет `fuzz/` (посев из `examples/`) | Валидация снапшота ручная и длинная — её ломают malformed-входы; property-тесты штатные пути покрывают, мутации — нет |
| Coverage-гейт gcovr `--fail-under-line` | Порог покрытия ратифицирует измеренное, а не желаемое: регресс покрытия виден в CI, а не по ощущениям |
| Архитектурный тест `check_ui_includes.sh` | Инвариант 7 в машинном виде: ui включает только фасад app; срабатывание = сигнал расширить read-API Controller, а не ослабить проверку |
| `include(CTest)` + `add_subdirectory(tests)` без guard `EXISTS` | Пропажа каталога тестов должна ронять configure, а не молча отключать тесты (2026-10-16: перенос tests/ в docs/ выпал из-за guard'а) |
| GoogleTest: `find_package` с FetchContent-фолбэком, пин v1.14.0 | CI без предустановленного gtest; пин тега — воспроизводимость |
| `RAVEL_REPO_ROOT` для тестов на golden-файлы | cwd бинаря при запуске ctest не гарантирован — тесты должны находить `examples/` из любого каталога |
| Сохранение через temp-файл + `rename` | Краш посередине записи не должен оставлять битый файл на месте целевого |
| `.editorconfig` | Единый стиль концов строк/отступов между VS, VS Code и прочими редакторами — формат-гейт ловит C++, но не JSON/доки |

Сквозная логика инфраструктуры: три кластера гарантий вокруг одного стека.

1. **Воспроизводимость** (пины форматтера/tidy/gtest, единые каталоги вывода,
   `/Brepro`) — любая сборка, локальная или в CI, бит-в-бит сравнима; это
   превращает «у меня работает» в проверяемое утверждение.
2. **Корректность на границах** (санитайзеры, fuzz, валидация снапшота,
   temp+rename) — закрывают именно те классы дефектов, которые unit-тесты
   ловят плохо: off-by-one в ручном индексировании, malformed-входы,
   частичная запись файла. Прямое следствие требования R6 «корректность
   важнее скорости».
3. **Дисциплина архитектурных границ в машинном виде**
   (`check_ui_includes.sh`, guard'ы CTest) — инварианты слоёв из §4 не
   зависят от дисциплины конкретного коммита.

## 7. Рассмотрено и отклонено

| Альтернатива | Причина отказа (привязка к требованию) |
|---|---|
| Electron / TypeScript / веб-стек | Тащит рантайм браузера и асинхронную модель ради офлайн single-user приложения (R1); экосистемные плюсы (сеть, коллаборация) закрывают отсутствующие требования |
| Qt Quick (QML/JS) | Сильна там, где слаб Ravel: touch, мобильные платформы, дизайнерская итерация. Advisors — paint-контроль (R4); второй язык в кодовой базе размывает границу core/UI и усложняет отладку (R8) |
| Python (+PyQt/PySide) | Латентность раскладки и отрисовки недетерминирована; упаковка десктопного приложения тяжелее, чем кажется; типовые гарантии слабее для R6 |
| Rust | Памятная модель для R6, но кривая обучения против R8: риск «бороться с borrow checker вместо проектировать граф». Окно стека уже закрыто CMake+Qt; переписывание ради переписывания отклонено |
| `QJsonDocument` (Qt JSON) | Связывает storage с Qt, ломая architecture §1.1 и CI без Qt (см. §5) |
| RapidJSON | Выигрыш в скорости не на том свойстве: нагрузка — валидация, не throughput (см. §5) |

## 8. Признанные риски и митигации

- **Скорость разработки на C++ ниже скриптовых стеков** — удерживается
  компактностью области (R5: 10³ узлов, нет сети/плагинов) и инфраструктурой
  из §6: формат, tidy, санитайзеры и фаззинг возвращают время, съеденное
  на типах.
- **Безопасность памяти** — компенсируется дисциплиной (RAII, нет владеющих
  raw-указателей в модели), ASan/UBSan на каждом push и fuzz-таргетом на
  границе ввода.
- **Widgets выглядит «не как современный веб»** — принято осознанно: язык
  продукта строится кастомной отрисовкой advisors (R4), шаблонные контролы
  почти не используются.
- **Стек нетипичен для индустрии PKM** — принято: требования Ravel
  (локальный, ручной, офлайн) смещены от типичных PKM (синхронизация,
  коллаборация, плагины). Граница `GraphSnapshot` делает стоимость смены
  сериализации/хранения ограниченной, если требования изменятся.

## 9. Вывод

Стек сознательно скучный там, где продукту всё равно (сборка, тесты,
формат, CI), и точно заточенный там, где Ravel отличается (раскладка как
ценность — C++23, advisors как paint-грамматика — Widgets, файл как
контракт — nlohmann/json). Личный фактор компетентности заявлен открыто и
удерживается в рамках критерия «стоимость владения»: каждое решение в §3–§6
привязано к конкретному требованию из §1 и проверяется в CI, а не апеллирует
к предпочтениям.
